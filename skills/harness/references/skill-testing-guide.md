# Skill Testing Guide

Testing methodology for skills and agent definitions generated by the harness. Reference this in Phase 6 for validation and in Phase 7 for iterative improvement.

## Why Test Skills

A skill that doesn't trigger is invisible. A skill that triggers incorrectly is annoying. A skill that triggers correctly but produces bad output is dangerous. Testing catches all three.

**The testing hierarchy:**
1. **Trigger testing** — does the skill activate for the right prompts?
2. **Structural testing** — does the skill have all required components?
3. **Behavioral testing** — does the skill produce correct output?
4. **Comparative testing** — is the skill better than no skill at all?

## Trigger Testing

### Writing Test Prompts

For each skill, write two sets of prompts:

**Should-trigger prompts (8-10 per skill):**
- Explicit: "run the [skill name]"
- Natural: "[domain verb] the [domain noun]" (e.g., "review the code," "migrate the endpoints")
- Casual: "can you [task]?" or "hey [task]"
- Terse: "[verb] [noun]" (e.g., "deploy api")
- Verbose: "I need you to [detailed description of the task]"
- Follow-up: "try again," "re-run it," "update the [thing]"
- Implicit: descriptions of the outcome without naming the skill

**Should-NOT-trigger prompts (8-10 per skill):**
- Adjacent: tasks that belong to a different skill in the same harness
- Similar-sounding: tasks that use similar words but mean different things
- Unrelated: tasks that shouldn't activate any harness skill
- Ambiguous: tasks where the right skill is genuinely unclear

### Near-Miss Boundary Cases

The most valuable test prompts are **near-misses** — prompts right at the boundary between triggering and not triggering. These expose weak spots in the description.

**Example for a deployment skill:**
- Should trigger: "deploy to staging" → ✅
- Should trigger: "push to production" → ❓ (does the description include "push"?)
- Should NOT trigger: "push the code to GitHub" → ❓ (is "push" too broad?)
- Should trigger: "release the new version" → ❓ (does the description include "release"?)

### Trigger Evaluation Method

For each test prompt:
1. Read ONLY the skill's name and description (not the body)
2. Ask: "Given this prompt, would Claude select this skill?"
3. Rate: DEFINITE, LIKELY, UNLIKELY, DEFINITELY_NOT
4. For should-trigger prompts: DEFINITE or LIKELY = pass
5. For should-NOT-trigger prompts: UNLIKELY or DEFINITELY_NOT = pass

**Score: (passes / total) for each category.**
- Should-trigger score < 80% → description needs strengthening
- Should-NOT-trigger score < 80% → description needs narrowing or body needs "When NOT to use" section

### Trigger Improvement Loop

When a trigger test fails:

1. **Should-trigger failed:** Add the missing phrase or keyword to the description
2. **Should-NOT-trigger failed:** Add a "When NOT to use" section in the SKILL.md body (not in the description — the description should stay inclusive)
3. Re-test after changes

## Structural Testing

### Required Components Checklist

| Component | Required | Check |
|-----------|----------|-------|
| YAML frontmatter with `name` | Yes | Name matches filename convention |
| YAML frontmatter with `description` | Yes | Non-empty, <200 words |
| One-paragraph summary | Yes | Explains what and why |
| Iron Law | Yes | Single unbreakable rule, ALL CAPS |
| "When to Use" section | Yes | 3+ conditions |
| Process section | Yes | Clear workflow, numbered or graphed |
| Red Flags table | Yes | 5+ entries |
| Integration section | Yes | Lists connections to other skills/agents |
| References (if >500 lines) | Conditional | Overflow content in references/ |
| Error handling | Recommended | What to do when things go wrong |

### Agent Definition Checklist

| Component | Required | Check |
|-----------|----------|-------|
| Core Role section | Yes | 2-3 sentences, clear responsibility |
| Work Principles | Yes | 3+ numbered principles with reasons |
| Input Protocol | Yes | What the agent receives, format |
| Output Protocol | Yes | What the agent produces, completion signal |
| Team Communication Protocol | If Agent Teams | Reports to, receives from, shares with |
| Error Handling table | Yes | Error types and actions |
| Domain Knowledge | Recommended | Specific to this agent's expertise |
| Model specified in Agent calls | Yes | opus, sonnet, or haiku — never default |

## Behavioral Testing

### With-Skill vs Without-Skill Comparison

The gold standard for skill testing: does the skill actually improve output?

**Method:**
1. Pick a representative task for the skill
2. Spawn two subagents simultaneously:
   - **Agent A:** Has the skill loaded (via the agent definition or by including the SKILL.md content in the prompt)
   - **Agent B:** No skill, just the raw task description
3. Compare outputs on predefined criteria

**Comparison criteria:**
- **Completeness:** Did the output cover all requirements?
- **Correctness:** Is the output factually/technically correct?
- **Structure:** Is the output well-organized?
- **Domain adherence:** Does the output follow domain conventions?
- **Error handling:** Does the output handle edge cases?

**Expected result:** Agent A should score higher on domain adherence and structure (the skill's value). If Agent A doesn't clearly beat Agent B, the skill is adding overhead without value — simplify or remove it.

### Assertion-Based Scoring

Define specific, binary assertions for each test:

**Good assertions:**
- "Output includes a section titled 'Error Handling'" → binary pass/fail
- "Generated code compiles without errors" → binary pass/fail
- "Agent definition includes Communication Protocol section" → binary pass/fail

**Bad assertions (non-discriminating):**
- "Output is well-written" → subjective, both agents will likely satisfy this
- "Code follows best practices" → too vague to evaluate
- "Response is helpful" → always true for both agents

**Non-discriminating assertions** are assertions that pass for BOTH the with-skill and without-skill agents. They waste evaluation effort. If an assertion passes for both agents in 3+ tests, remove it — it's not testing the skill's value.

### Specialized Evaluation Agents

For systematic evaluation, use evaluation-specific subagents:

**Grader Agent:**
- Receives: the output + the assertion list
- Produces: pass/fail for each assertion + overall score
- No access to whether this was with-skill or without-skill (blind grading)

**Comparator Agent:**
- Receives: Output A and Output B (labels randomized)
- Produces: which output is better on each criterion + overall winner
- Blind comparison — doesn't know which had the skill

**Analyzer Agent:**
- Receives: multiple grading/comparison results
- Produces: statistical summary, patterns, recommendations
- Identifies: which assertions are discriminating, which criteria the skill improves

## Iterative Improvement

### The Feedback Loop

```
Write skill → Test triggers → Test behavior → Analyze results → Improve skill → Re-test
```

### Common Improvement Actions

| Finding | Action |
|---------|--------|
| Trigger score too low | Add phrases to description |
| False triggers too high | Add "When NOT to use" section |
| With-skill ≈ without-skill | Skill instructions are too generic. Add domain-specific knowledge. |
| With-skill worse than without | Skill is over-constraining. Remove or relax the problematic rules. |
| Inconsistent output format | Add explicit output format with example |
| Missing edge case handling | Add error handling table |
| Too many tokens loaded | Move content to references/ |

### Generalization Rule

When fixing a skill based on test results, **generalize the fix** — don't overfit to the specific test case.

- **Bad fix:** "When the input mentions 'authentication,' check for OWASP A01"
  - This overfits to one test case. What about "login"? "auth"? "session management"?
- **Good fix:** "When the input involves user identity, authentication, or authorization, check for OWASP A01-A07"
  - This generalizes to all security-related inputs.

### Removal Rule

If an instruction in the skill doesn't improve the with-skill score compared to without-skill across 3+ test cases, remove it. It's consuming tokens without adding value.

**Corollary:** Don't add instructions preemptively. Add them when testing reveals a gap. This keeps skills lean.

## Test Workspace Structure

For systematic testing, use this directory structure:

```
_workspace/harness/testing/
├── iteration-1/
│   ├── trigger-results.md          # Trigger test scores
│   ├── test-prompts.md             # Test prompt sets
│   ├── with-skill-outputs/         # Outputs from with-skill agent
│   │   ├── test-1.md
│   │   └── test-2.md
│   ├── without-skill-outputs/      # Outputs from without-skill agent
│   │   ├── test-1.md
│   │   └── test-2.md
│   ├── grading-results.md          # Assertion scoring
│   ├── comparison-results.md       # Blind comparisons
│   └── improvement-notes.md        # What to change for next iteration
├── iteration-2/
│   └── ...
└── summary.md                      # Cross-iteration analysis
```

### When to Stop Testing

Stop iterating when:
1. Trigger score ≥ 90% for both should-trigger and should-NOT-trigger
2. With-skill consistently beats without-skill on discriminating assertions
3. Two consecutive iterations show no improvement (convergence)

Don't pursue perfection. A skill that triggers 90% of the time and improves output 80% of the time is production-ready. The remaining 10-20% will be caught by Phase 7 (Evolution) through real-world usage feedback.

## Quick Test Protocol

For time-constrained validation (Phase 6 of the harness), use this abbreviated protocol:

1. **5 trigger tests** (3 should-trigger, 2 should-NOT-trigger)
2. **Structural checklist** (pass all required components)
3. **1 behavioral test** (representative task, with-skill vs without-skill)
4. **Verdict:**
   - All trigger tests pass + structure complete + behavioral test wins → READY
   - Any trigger test fails → fix description, re-test triggers only
   - Structure incomplete → fix structure
   - Behavioral test loses → investigate and fix or simplify

This takes 5-10 minutes per skill and catches the most common issues.
